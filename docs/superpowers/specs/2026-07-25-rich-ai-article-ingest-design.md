# 富媒体 AI 文章采集设计

## 目标

把现有“RSS 标题 + 短摘要 + 原文链接”的候选内容升级为可正常阅读的中文图文文章。首轮只改造 5 篇已发布的本地文章，用于验证正文质量、图片展示、作者轮换和时间分布；不连接或修改生产数据库。

成功标准：

- 每篇正文约 800–1500 个中文字符，包含 3–6 个有意义的小节，而不是固定的“摘要／为什么值得阅读／来源”模板。
- 每篇至少有 1 张封面图；原文存在适合正文使用的图片时，最多再使用 2 张正文图。
- 5 篇文章来自至少 5 个不同来源。
- 作者来自显式配置的现有活跃用户白名单，连续文章不使用同一作者。
- 列表显示时间分布在最近 30 天内；原始来源发布时间继续保存在 `article_source.source_published_at`。
- 每篇保留来源名称、原文链接和“基于公开来源整理”的说明，不把整理稿伪装成原作者全文。

## 方案比较

### 方案 A：只使用 RSS 内容扩写

优点是速度快、失败面小；缺点是输入信息不足，模型容易生成空泛内容或补充未经来源支持的事实，也无法稳定获得正文图片。当前短模板就是这个方案的结果，因此不采用。

### 方案 B：为每个来源编写专用抓取器

优点是正文和图片提取精确；缺点是实现与维护成本高，页面结构变化时需要逐个修复，不适合先验证 5 篇内容质量。

### 方案 C：通用正文抽取 + 来源适配规则

先用通用 HTML 正文抽取器读取标题、段落、标题层级和图片，再用少量来源规则排除导航、推荐区、头像、图标等噪声；页面无法通用抽取时才进入来源适配器或跳过。

采用方案 C。它能快速覆盖多个公开来源，也保留后续针对高价值来源逐步增强的空间。

## 数据流

```text
候选原文 URL
  → 安全 HTTP 获取
  → HTML 正文与图片候选抽取
  → 内容质量检查
  → Ollama 基于来源材料重写中文长文
  → 图片下载、校验、转码并暂存
  → 人工审批
  → 文章、作者、图片、封面、来源信息单事务关联
```

抓取阶段只访问 `http`/`https` 公网地址，拒绝环回、局域网、链路本地地址和重定向到这些地址的请求，避免 SSRF。每页设置超时、响应体大小上限和图片数量上限。

## 正文抽取与重写

新增独立于 Koa 的原文提取模块。它从 HTML 中提取：

- 页面标题、描述和 canonical URL；
- 主体段落和 `h1`–`h3` 标题；
- `og:image`、正文图片 URL、替代文本和图注；
- 页面声明的作者与发布时间（仅作来源元数据，不映射成站内作者）。

进入重写前必须满足最低质量门槛：

- 正文纯文本不少于 600 个字符；
- 至少有 4 个非重复段落；
- canonical URL 与候选来源一致；
- 图片 URL 通过安全地址和媒体类型校验。

Ollama 输出结构化结果：中文标题、导语、3–6 个章节、结语、关键词和图片插入建议。提示词只允许使用抽取到的来源材料；输出不得声称站内作者亲历事件，不复制大段原文，不生成来源中不存在的数字、人物或地点。

最终正文使用现有 Tiptap JSON：

1. 导语；
2. 封面或首张正文图；
3. 按输出章节生成二级标题与段落；
4. 在建议位置插入最多 2 张正文图；
5. 文末添加来源说明和原文链接。

## 图片处理

首轮从原文页面选择最多 3 张图片：

- `og:image` 优先作为封面；
- 正文图片按像素面积、与正文位置、替代文本质量排序；
- 排除小于 480×270 的图片、图标、头像、Logo、追踪像素和重复图片；
- 只接受 JPEG、PNG、WebP；
- 单图下载上限 8 MB，总图片上限 20 MB。

图片下载到临时目录，使用现有图片处理能力获取尺寸并生成本站文件名。发布时写入 `file` 和 `image_meta`，封面图设置 `is_cover = TRUE`，Tiptap 图片节点引用对应 `imageId`。数据库事务失败时删除本轮新文件，避免磁盘孤儿。

原图仍受来源许可约束。生产自动化只允许启用已确认可转载图片的来源；许可不明确的来源应跳过原图，后续可接入自有图库或生成式封面。

## 现有用户自动轮换

不创建机器人账号。通过 `INGEST_AUTHOR_IDS` 配置允许参与的现有用户 ID，例如 `1,2,3,4,5`。启动时解析并验证：

- 用户存在且 `status = 0`；
- 用户资料与头像可用；
- 至少有 2 个可用作者，否则拒绝批量发布。

作者选择是确定性的而不是每次真随机：

1. 使用整个批次 canonical URL 集合的稳定哈希决定作者池起点；
2. 按候选 canonical URL 的稳定顺序循环分配白名单作者；
3. 作者数不少于文章数时，每篇使用不同作者；作者较少时也不会连续重复；
4. 同一批次重试时保持相同作者。

这样重复执行不会导致作者漂移，也不需要人工登录或切换账号。白名单只应包含站点所有者明确允许用于自动整理内容的账号。

## 时间分布

`article.create_at` 表示站内展示发布时间，`article_source.source_published_at` 表示原文发布时间，两者不混用。

首轮 5 篇采用确定性的 30 天回填分布：

- 将最近 30 天分成 5 个等宽时间桶；
- 每篇分配到一个不同时间桶；
- 使用 canonical URL 哈希在桶内生成稳定偏移；
- 不晚于当前时间，也不早于候选的采集窗口；
- 重试后时间不变化。

日常定时任务不做一个月回填，使用实际入库时间；来源发布时间仍在详情页来源区域展示。确定性偏移既避免 5 篇拥有完全相同时间，又不会因重跑不断变化。

## 首轮 5 篇策略

从当前已发布的 10 篇聚合文章中选择 5 个不同来源，优先选择能完整抽取正文且至少有一张合格图片的页面。改造采用原文章 ID 原位更新，保留点赞、收藏、浏览量、标签和 `article_source` 关系。

其余 5 篇暂不删除、不覆盖，便于对比；在首轮结果确认后再决定改造或下线。

## 失败处理

- 页面拒绝访问、正文过短或无合格图片：标记富媒体处理失败，不修改现有文章。
- 模型输出不符合结构或长度：记录原因，可重试；不发布半成品。
- 图片下载失败：换用下一候选图；全部失败则跳过该文章。
- 任一数据库关系写入失败：回滚文章、图片和作者变更，并清理新下载文件。
- 单篇失败不阻塞其他文章，但最终必须明确报告成功与失败列表。

## 测试

单元测试覆盖：

- HTML 主体、canonical、标题层级和图片提取；
- 私网地址、错误媒体类型、超大响应和重定向拦截；
- 图片去重、尺寸筛选和封面选择；
- 中文结构化输出校验与 Tiptap 图文构造；
- 现有用户白名单验证、稳定分配与相邻去重；
- 30 天时间桶的范围、稳定性和单调分布；
- 更新文章、绑定图片与失败回滚。

集成验证覆盖：

- 本地数据库中 5 篇文章分别拥有有效作者、时间、来源和封面；
- 详情 API 返回 800–1500 字正文及可访问的本地图片 URL；
- 列表 API 返回 5 个不同来源的封面，时间跨越最近 30 天；
- 旧版短模板文章和普通用户文章不受影响。
