# 导入文章媒体链路修复

> 历史设计/实施快照：保留当时的步骤、版本和勾选状态，不代表当前待办；不要直接重放其中的安装、迁移或发布命令。当前入口见[文档导航](../../README.md)。

用户已授权直接推进第二步：修复导入入口并补齐历史遗漏，常规实现自行判断。PG 升级、账单复核和本地媒体清理不在本步范围。

生产基线为 16bbba5。两个回填入口复制 original/small 到 public，仓储创建 file/image_meta，但没有 local media_object 登记或 R2 promotion。替换操作目前无条件重建 file ID；有 R2 登记后，这会失去旧对象身份。提交后清理异常还会误入复制文件补偿分支。

选择复用现有媒体登记和 promotion 服务。一次性补传不能修复入口；另建上传器会重复容量、校验和幂等规则。实现应将已提交的文章状态与媒体同步状态分别报告，上传失败时保留可读取的本地文件，重试不能复制文章、文件 ID 或 R2 对象。

本地登记复用 `registerCandidate` / 媒体清单能力，R2 上传复用 `PublishedImagePromotionService` / `MediaPromotionService`。接线使用同一 ingest database 配置，避免 CLI 另开不同数据库。遵守写入暂停/本地模式。不得因为 R2 暂停而漏掉本地登记。

新增、替换及重试都要测试。替换中复用未变化文件的 ID 和登记；移除或变化的旧媒体必须保持可追踪且可恢复，不得级联删除 media_object 后留下 R2 孤儿。优先复用现有生命周期能力，避免新建队列或媒体框架。提交前失败仅补偿本次新复制文件；提交后失败绝不删除已发布源文件。

验收分两层：本地自动测试和真实 PG/模拟对象存储集成验证创建、替换、失败重试、幂等；生产按固定 12 个 file ID、24 个变体的校验清单补登记和上传，只新增缺失项，保留所有现有对象和文件。生产全量对账应为 0，R2 217 个、media_object 434 行（无并发业务变化时），媒体与 API 读取通过。保存当前备份及回滚材料后部署，仅发布本次改动。完成后刷新备份并安全暂停。
